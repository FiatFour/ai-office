# Set B pre-registration

Registered before any Set B run. Source: `docs/plans/agent-works-plan.md`, Phase 3 ticket P3-1. Code: `bench/setb/`. The G1 thresholds in `bench/report.ts` do not change.

## Why Set B changed

The old rule was "passes when the operator merges unchanged". Root now merges, so that is self-graded. Set B now uses real open issues of FiatFour/ai-office itself, real CI on the public repo, and a blind judge that is not the factory reviewer.

## Judge

- A fresh verifier per PR: `claude -p --model opus --effort xhigh --tools "" --no-session-persistence`. Never the factory reviewer. It gets the issue item, the diff and the CI result. `renderPrompt` shows no label, head sha, branch, arm or PR number, and `buildPacket` refuses a diff or issue text that holds a co-author trailer, a `Claude-Session:` line, the agent mail address, a generated-by line, or one of the PR's own strings (its branch, the ticket id in the branch, its labels, read from the PR by `fetchPacket`). No generic branch pattern: a test file may honestly contain `aw/bench/t-0a1b2c3d-r1`. A refusal hits that packet only. The judge run records it as `unreadable` (reason `unreadable by leak`) and `grade` scores that PR a fail with the reason in the note.
- Fixed rubric (`bench/setb/rubric.ts`): MERGE AS IS, MERGE AFTER EDITS (the edit as a diff block), REJECT. The judge prompt states a strict contract: the reply ends with exactly one final line, `VERDICT: MERGE AS IS`, `VERDICT: MERGE AFTER EDITS` or `VERDICT: REJECT`, nothing after it, and no earlier line begins with the word VERDICT and a colon. The reader checks only that. The final non-empty line must be one such line; markdown emphasis (`*`, `_`), backticks, a trailing period, any case and CRLF are tolerated, nothing else (a heading or quote mark, prose before it, a second verdict, a trailing clause are not). Any earlier line outside a code fence that begins, after markdown marks and a heading, quote or list marker are stripped, with the word `VERDICT` and a colon makes the reply unreadable. A final line inside a code fence that is still open (a diff block cut off at the end of the reply) is unreadable. Nothing else is flagged: no proximity test, no Unicode folding, no word list in other languages, no fence-parity guess about ordinary prose. **A judge reply that obeys the prompt cannot be misread, and a reply that disobeys it is the judge's failure**, scored as unreadable, rerun under the retry rule below. Earlier rounds widened a fuzzy stray-verdict detector four times; each widening made false positives that cost real passes, so it was removed. The guard against a judge that does not follow the contract, or reads loosely, is empirical: the seeded-bad PR calibration below voids the run if the judge passes either planted defect or cannot be read on them. The rubric text holds no line the reader would take for a verdict. A diff block that only quotes the original diff is not counted as edit lines. A reply with no verdict, or edits without a diff, is unreadable. An empty judge reply with exit 0 is a failed `claude` call (rerun, no retry bias), not an unreadable reply.
- One bad packet never kills the batch. Each packet gets at most 3 judge calls (the first and two reruns, `MAX_ATTEMPTS`), for an unreadable reply or a failed `claude` call. **Retry rule:** a packet that reached MERGE AS IS only after an earlier reply was unreadable (not a failed call, which has no reply) is graded a fail, recorded as `unreadable` with that reason, because a fresh draw after an unreadable first reply could otherwise only move toward a merge. The number of judge calls is kept as `attempts` and shown in the graded row note (`judge calls: N`), in `judgeAttempts` and in the report column `judge calls`. After that the packet is recorded as `unreadable` with the reason and the attempt count, and the verdicts already obtained are written. A `gh` failure while building a packet (a compare 404 on a force-pushed-away ready sha, more than 100 check runs) records that packet as `unreadable by fetch` the same way. `grade` scores an unreadable PR a fail with the reason in the note. On a seeded-bad PR, three failed attempts void the run.
- A void ends Set B at the third one (`MAX_VOIDS` = 3). The count is the larger of two records. (1) Each void is logged to one fixed file, `<dir>/voids/<sha256 of tasks.json>.jsonl`, which does not depend on `--out`. It is a tracked `.jsonl`, not a gitignored `.log`: commit it with the run, so deleting it shows in `git status`. (2) Every file in the run directory (`--dir`) and in its fixed `judged/` folder whose body is a judge output with `voided` set counts as one void, whatever its name. `judge` refuses an `--out` that is not a `.json` file directly inside `<dir>/judged/` (and creates the folder), so a new `--out` directory cannot start the count again, and `rm -rf voids` does not reset it. The void is written to the log (with fsync) before the output file, so a failed output write after the judge ran (a read-only `judged/`, a dangling symlink at the `--out` name) does not lose it. **The count can still be lowered by removing or altering the voided outputs** (rename to `.bak`, delete the `voided` key, move to `judged/old/`, replace with a symlink, run from a copy of `--dir`) together with the log. The committed voids log is the real guard: root runs `git status` and checks that the tracked log and outputs are unchanged before every judge run; the code does not claim to stop edits made on purpose. `judge` refuses to run once that count is 3. `judge` also refuses an `--out` that already exists, and never overwrites it, so each rerun names a new file. So at most 2 reruns after a void; a third void means Set B is reported as not run.
- Calibration: the same batch holds 2 seeded-bad PRs (`bench/setb/calibration/seeded.json`: a fix that deletes the drive-path guard, a fix that hard-codes the two example inputs; both CI green on the frozen base: seeded PR 0 also deletes the one `closure.test.ts` case it breaks, as a real bad PR would). The check count in a seeded CI note is not written down anywhere: at judge time each seeded packet takes the count of one real PR of the same run, drawn at random among the real PRs with green CI (among any real PRs with check runs when none is green), and goes through the same `ciFrom` as a real packet. When the real counts are all equal, that is the count every seeded PR shows. A run in which no real packet has check runs is refused before any judge call. A real bench PR on these tasks is expected to show 22 check runs, not the 26 of the pinned base `56db6a1` (inferred: `56db6a1` also ran the 4 jobs of `redteam.yml`, whose `pull_request` path filter matches none of the 10 tasks' files, and PR #51 head `efdab31`, which matches none either, showed 22). The frozen base itself was not green: 14 success, 1 failure, 3 cancelled. The seeded PRs are built to look real: the issue text comes from `tasks.json`, the CI note comes from `ciFrom`, and the diffs are `git diff` output that `git apply --check` accepts on the frozen base (a test checks it). If the judge returns anything but REJECT for either (MERGE AS IS or MERGE AFTER EDITS), or cannot be read on either, the whole run is void and rerun. This is stricter than the ticket, which would void only on MERGE AS IS: no machine can decide whether a judge's edit repairs the planted defect, so any non-REJECT is treated as a pass. It is cheaper than a loose calibration that lets a soft judge through.

## Pass rule

A PR passes iff all hold at the ready head sha:

1. CI is green (all check runs completed, none failed, at least one success).
2. The judge said MERGE AS IS.
3. The head did not move: the PR head, the judged head and the CI head all equal the ready head sha.
4. The PR touches nothing under `.github/`.

MERGE AFTER EDITS is a fail, with the edit lines recorded. A moved head is a fail. Root merges at most one PR per task, the judge's pick. A PR that is not merged still counts by this rule, so the pass rate does not depend on which twin root picks.

## Arm runners (P3-2)

- `node bench/setb/run.ts drive|entries|settle|grade-all|close|reconcile`. `drive` needs `AW_BENCH_LOGIN_CONFIRMED=1`. It refuses `GH_HOST`; every `gh` call it makes names `--hostname github.com`.
- **Resume.** Before the first remote write of an arm, `drive` appends an `intent` record (task, arm, salt, branch, base, base sha) to `runs.jsonl` and fsyncs it. A rerun of the same task and arm reuses that intent (same salt, same branch and base), never a fresh salt. Policy on resume, stated once: an open PR on the branch that the arm accepts is **reused** (the baseline's PR is complete once opened; a factory PR counts when `vega` reviewed its head, `vega`'s last review of that head does not ask for changes, and no review listed after it, from anyone and on any commit, asks for changes; the live run's stop rule is looser and takes any `vega` review of the head that does not ask for changes) and recorded as `done` (its tokens were not recorded and the note says so); any other open PR on that branch is **closed** and the branch and base refs are **deleted**, and the arm starts again on the same names. The result is one open PR per task and arm; a closed, labelled `aw-bench` PR from an interrupted factory run can remain on GitHub. A factory arm's HQ home is wiped on such a restart.
- **One driver at a time.** `drive`, `close` and `reconcile` take `<out>/runs.jsonl.lock` (created with `O_EXCL`, holding the pid, start time and command) before they read the journal's base or call the host, and release it on exit and on SIGINT, SIGTERM and SIGHUP. A second command exits 3 and names the holder. A lock whose pid no longer runs is taken over. An unreadable lock, or a leftover `runs.jsonl.lock.break`, is left for a person to delete. The lock covers one `--out`; two different `--out` directories are not guarded against each other, and `close` sweeps every bench ref on the remote.
- **Torn journal line.** A last line that a crash cut short is skipped and printed by every command. `reconcile` also puts it in its report and exits 6. `drive` moves it to `runs.jsonl.torn` before it appends. An intent is fsynced whole before any remote write, so a torn intent has no remote write behind it. A broken line anywhere else still stops the command.
- **`close` and `reconcile` read the remote, not the journal.** Both list the refs under `aw/bench/` and `aw-bench-base/` and every PR whose head is under `aw/bench/` or that carries the `aw-bench` label, so a PR killed before it was labelled is still found. `close` closes every open one and deletes every ref found, including refs with no PR (a run killed after `seedBase` or the push), and refuses when a bench PR is merged. `reconcile` only reports (refs, PRs, refs and PRs the journal has no intent for, intents with no final record) and exits 6 when something is not in the journal. A test kills the driver after `seedBase`, after the push and after `openChange` against the fake host and reruns: one PR per task and arm, nothing orphaned, and `close` deletes every ref.
- **Statuses.** `done` and `failed` are final. `quota` (a usage limit: stop, exit 75), `transient` (a provider overload or rate limit: `API Error: 429`, `API Error: 529`, `overloaded_error`, `rate_limit_error`), `auth` (STOP file, exit 5) and `aborted` are not final, are not counted against either arm, and are resumable. Each transient stop is its own record; an arm gets at most 3 (`TRANSIENT_CAP`), with a wait of 1 and then 2 minutes, and the third one makes `drive` stop with exit 75 for root to decide. `claude`'s stderr is read: when stdout has no result line, the stderr line that states a stop becomes the failure text. Only a provider message at the start of a line, or at the start of what `claude ended with <subtype>:` reports, matches (`You've hit your limit` with its separator, `usage limit reached`, `API Error: 429`, `API Error: 529`, `overloaded_error`, `Failed to authenticate`, `OAuth token revoked`): a task that says "rate-limit" and a model result that says "You've hit your max turns" are not stops. An auth line wins over any other stop, wherever each was printed, unless `claude` reported success. A `claude` that exits 0 and prints nothing is `transient`. When the result line says only `Execution error`, the stop is read from stderr. A host refusal after round 0 is `failed` (final), like the baseline's refused push.
- **Arm limits actually used** (asymmetries, with the direction each is expected to push): baseline 60 minutes in all, one session, no review round; factory 180 minutes in all and 40 turns and 30 minutes per session (the `claudeCode` defaults, the baseline has the same per-session limits). The factory gets reviewer rounds from `vega` and the baseline gets none: expected to favour the factory on correctness. Neither arm gets CI feedback: the factory is not told when the PR's checks fail, and neither can retry on a red CI. The factory has more wall time: expected to favour the factory, and the wall and token columns are reported next to the pass rate so root can weigh that.
- **Neither arm can delete a file.** The baseline pushes the files its session committed as added or modified (`--diff-filter=AM`), and the factory's pushes go through the same host call; a task that needs a deletion cannot be completed by either. No frozen task needs one, and the judge sees the diff as pushed.
- **The arms are visibly different on GitHub, and this is a known limit, not something the bench hides.** A factory PR has several commits, reviews from `vega` and two or more review rounds; the baseline PR has one commit and no review. The title, commit message and body use one template for both (`bench/t-xxxx-r1: <title>`, `Work order ... Opened by an Agent Works worker`), so the text is no longer a tell, but the commit count and the reviews are. The judge packet is blind (the diff and the CI text only, no PR page). **Root must not read PR pages, commit lists or reviews before judging.**

## Columns

Per row (`bench/model.ts`): `editLines`, `judgeMinutes`, `rootMinutes`, `inferredWindows`, next to the existing `humanMinutes` (operator, expected 0). `bench/report.ts` shows them per task and arm. The Human minutes verdict uses operator minutes against the threshold of 10; root and judge wall minutes are printed beside it, separately, never summed in. A Set B baseline pass rate line (INFO, no bar) sits next to the factory verdicts. The baseline line and the new columns appear only when live Set B rows exist: `node bench/report.ts` on the Set A rows is byte identical to `bench/results/report-set-a.md`, and `bench/setb/test/report.test.ts` diffs it against that file.

## Cost

Threshold unchanged: at most 1 five-hour window per 5 merged PRs. Windows are n/a today, so each row records tokens and `inferredWindows = tokens / tokensPerWindow`. `tokensPerWindow` comes from `bench/setb/window.json`, which holds one measured calibration window and is `null` until someone measures it; with `null` the cost verdict stays UNMEASURED. A verdict from inferred windows says "(inferred from tokens)". Estimate before any run: about 15M tokens, 4 to 8 windows over 1 to 2 days (inferred from Set A: 6.9M tokens for 20 runs, real issues 2 to 3 times bigger).

## Run it

```
node bench/setb/cli.ts check
node bench/setb/cli.ts label --entries entries.json --key key.json
AW_BENCH_LOGIN_CONFIRMED=1 node bench/setb/cli.ts judge --key key.json --out bench/setb/judged/judged.json --home <login home>
node bench/setb/cli.ts grade --key key.json --judged bench/setb/judged/judged.json --label pr-xxxxxxxx --out rows.jsonl --operator-minutes 0 --root-minutes N
node bench/report.ts rows.jsonl
```

`entries.json` lists `{task, arm, pr, readyHeadSha}` and is the record of the ready head. `label` and `judge` and `check` all load the frozen list. `judge` builds every packet itself: the issue text from `tasks.json`, the diff from GitHub's compare of the PR base to `readyHeadSha` (so the diff is that head's, even if the PR moved), and the CI from the check runs of `readyHeadSha`. The CI `sha` is the head the check runs report, and a mismatch fails at grading. There is no hand-written `packets.json`. `grade` reads the PR head, the check runs and every page of the PR file list from GitHub with `gh`.

## Limits

- The judge is a model, not a maintainer. An operator spot-check of 3 merged PRs is optional and never blocks.
- The judge run, the calibration run and the window calibration have not been run: they spend subscription quota and need the bench login. The code paths are covered by tests with a fake model.
- The `host-hidden-path-allowed` mutant is anchored on the signature of `filePathProblem` in `server/githost/host.ts`, not its body, so a P3-5 edit inside it does not break the mutant. A rename of that function would, and the mutant then fails with `pattern not found`.
- The `git apply --check` test needs the frozen commit. A clone that lacks it (CI checks out at depth 1, and the perf job clones that shallow checkout with `--no-hardlinks`, whose origin is a local path that cannot serve a sha it lacks) fetches that one commit with `git fetch --depth=1 <remote> <sha>` into a scratch repo. The remote is `AW_FROZEN_REMOTE` when set (only that); else origin when it is not a local path; else, for a local origin, `GITHUB_SERVER_URL`/`GITHUB_REPOSITORY`, then origin's own origin up the chain, then origin itself. If no remote serves the commit the test fails loudly naming each remote tried. It never falls back to the working tree.
- `bench/test/mutants.mjs` is not extended: P3-4 owns it. The Set B mutants run with `node bench/setb/mutants.mjs` and need a CI job line in `ci.yml` (P3-4).
- #31 b: a failed arm's row note now keeps the tail of the message (about 300 characters, ending where the malformed verdict sits) and the whole message goes to `<out>.errors.log`. The 500-character head excerpt cut inside `server/agents/claude-code.ts` belongs to P3-5.
