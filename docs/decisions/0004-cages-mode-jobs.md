# ADR 0004. The cages mode derives each job from the reducer state

Status: proposed in P1-2, 2026-11-17. The operator may override any default below.

## Context

P1-2 runs one ticket to a reviewed PR that a person merges. The reducer in `packages/core` emits commands (`start_cage`, `request_review`, `send_review_to_author`, `notify_ready`, `close_task`) and HQ's outbox delivers each one at least once. An agent session runs for minutes, HQ can die at any point, and the git host is the only place where a PR, a review or a comment exists. HQ must never open a second PR, post a second review or brief, or merge.

## Decision

- **Commands are triggers, the state decides.** An executor only wakes the task. The mode computes the one job the task needs from the current state: `building` needs the author job, `qc` with changes requested needs a fix round, `qc` with a reviewer who has not reviewed the head needs a review, `merge` with no brief for the head needs a brief. A repeated command, a restart and a poll tick all run the same function, so the job that runs is the job the state still needs. On start HQ wakes every task.
- **Each job checks the host before it writes.** The author job looks for an open PR on `aw/<factory>/<task>` and adopts it. The fix job reads the head first and stops if it already moved. The review job looks for a review on the head that carries its marker (`<!-- agent-works:review worker=<w> verdict=<v> -->`). The brief job looks for a comment that carries `<!-- agent-works:merge-brief task=<t> head=<sha> -->`. A crash between a host write and HQ seeing it therefore repeats no write.
- **Jobs run in the background,** one at a time per task and in parallel across tasks, so the outbox drain stays short. A job that fails three times on the same head becomes a `job_failed` Action item. An author job that gives up sends `session_ended`, so the reducer moves the box back to the belt and raises `worker_ended_without_pr`.
- **Rounds come from the event log.** A round is a head on which a peer asked for changes. The mode replays review facts from the `events` table at start and keeps the count as events arrive, because the state row prunes facts of replaced heads. After three fix rounds the box stays in `qc` and the snapshot shows a `round_limit` Action item. The fourth request for changes gets no fix.
- **Action items are derived, not stored:** `ready_to_merge` (box at `merge` with a posted brief), `round_limit`, `website` (a proxy denial not yet allowed), `alert` (every `alert_human` command in the outbox) and `job_failed`. `POST /api/actions/allow {host}` adds the host to the egress allowlist, and the worker's own retry then goes through.
- **A worker is named by its host login.** This answers the G1 mapping question in the direction `docs/lifecycle.md` names: the hired name is the host login. With one host account (the scratch repo today), every PR and review comes from the same login. HQ then attributes a review it posted itself to the reviewer worker and keeps only a `changes` verdict. It records an approval as a `comment`, so with one account a box waits in `qc`, as G1 decided. The host's copy of that review has the author's login and the reducer refuses it.
- **GitHost writes pass one guard that reads the method, the path and the body.** `server/githost/host.ts` refuses every write that is not one of: create a tree, a commit or a ref, move a task ref forward, open a PR or MR, post a review, discussion, note or approval, post an issue comment. No merge endpoint is on the list. Each host client is bound to the configured repo or project and base branch: a call, reads included, that names another repo or project is refused, and a PR or MR must target the configured base. The configured GitLab project must be a namespace path, so a numeric id is refused. A write path that URL normalization changes (a query, a fragment, a dot segment) is refused. GitLab routes match by exact case. Each route lists the body keys it accepts and refuses any other key. That refuses `force`, `start_project` and `author_email` on a GitLab commit, `execute_filemode` on a commit action, `target_project_id` on an MR, `author` and `committer` on a GitHub commit, and `issue` on a GitHub PR. A new GitLab branch may start only from the base. Every branch HQ writes must be `aw/<factory>/<task>`, where each part is a letter or digit followed by up to 62 letters, digits, `_` or `-`. A ref update may not force. A pushed file may not have a hidden segment, a backslash, a symlink mode or a submodule mode.
- **The guard also refuses a body that is not safe to post** (see the premise below). Every text field of a write (`body`, `title`, `description`, `message`, `commit_message` and each line comment body) must pass `bodyProblem` in `server/githost/sanitize.ts`. Lines split on LF, CR, CRLF, LS, PS, NEL, VT and FF, the same set the quoting uses. A body fails when any line starts with a slash after quote, list, checkbox, indent, zero-width and Unicode-lookalike prefixes are stripped. Outside code spans and fences, it also fails on an `@` mention, raw HTML (only HQ's own `<!-- agent-works:... -->` marker lines pass) or a markdown link. A backslash-escaped backtick opens no code span. A backtick fence whose info string holds a backtick is not a fence, and a fence closes only on a bare fence line. An indented fence fails, because a list item can end it and show its contents as prose. A body over 60,000 characters fails.
- **HQ reaches the host through `gh api` and `glab api`,** so HQ never reads or stores a token.
- **The event record for P1-3 is `GET /api/events?after=`.** `node server/modes/events-export.ts <hq-url> <file>` writes it as `events.jsonl`.

## The premise this round attacked

Round 1 assumed that a write guard on the method and the path is enough to guarantee HQ never merges. That premise is false on GitLab. GitLab runs quick actions (`/merge`, `/approve`, `/assign`, ...) in a note or an MR description posted through the API, so `POST .../notes` with `/merge` on a line merges through an allowed endpoint. HQ posted untrusted text into exactly those bodies: the work order in the MR description, the reviewer body and each line comment, and the reviewer's comments again in the merge brief's `asked:` lines. The verifier showed `/merge` and `/approve` at line start in a rendered brief.

The fix makes the body part of what the guard checks, so the guard is again the single place that decides what HQ may send. Every composer quotes untrusted text through `server/githost/sanitize.ts` before it builds a body:

- `quoteBlock` puts the text in a fenced code block whose fence is longer than any backtick run in it. Each line starts with `│ `, so no quoted line can begin with a slash even if a host ignored the fence. It drops control and format characters and puts a word joiner after `#` before a digit, so `#12` neither links nor closes an issue. It cuts the text at 4,000 characters and says how much it cut.
- `inlineCode` makes a single-line code span (file names, check names, task ids, the work-order URL).
- `plainLine` keeps letters, digits and plain punctuation for titles and commit messages. It drops `@`, `#`, `<`, brackets and a slash that starts a word.

The ticket title, ticket body, ticket URL and risk reason, the reviewer body and line comments, the changed file names, the check names, and the brief's evidence and notes all pass through these. A property test (`server/test/sanitize.test.ts`, fast-check) generates hostile text from quick actions, lookalike slashes, zero-width and bidi characters, fences, mentions, HTML and links. It checks that no output line starts a quick action, and it sends every body through the real GitHub and GitLab clients to the fakes. Mutants remove each quoting site, the guard's body check, the lookalike set, the zero-width strip, the line marker, the mention rule and the length cap. Each one is caught.

GitHub has no quick actions, but mentions notify people and closing keywords close issues, so the same rule holds on both hosts.

## Writes that survive a kill

- **A round is one commit.** On GitHub, HQ builds the round with the git data API: one tree with every file of the round, one commit, then one ref write (create the task branch, or move it forward without force). A kill before the ref write leaves the branch where it was. A kill after it leaves the whole round. On GitLab, one `repository/commits` call already carries every file, so the round is atomic by construction. No real-kill test covers the GitLab push, because no GitLab account exists (G0). The job that was interrupted runs again from the state on restart: the fix job sees the head has not moved and pushes the whole round again, or sees it moved and stops. `server/test/kill-push.test.ts` kills a real HQ process with SIGKILL after the tree, after the commit and after the first branch move of the fix round, and checks that every reviewed head holds one complete round and that the approval covers the whole fix. A mutant that splits the push into two commits is caught.
- **A dedup marker counts only when HQ's own account wrote it.** Each host client reads its login once (`GET /user`). A brief marker counts only on a comment by the HQ login, and it must be a whole line. A review marker counts only on a review by the reviewer login, and it is anchored to a line too. A fix round and the brief's `asked:` lines take only line comments that the reviewer login wrote on the head being fixed. Another account's fake marker or drive-by comment changes nothing.
- **Lists are read to the last page.** Reviews, review comments, issue comments, MR notes, PR files, MR diffs, statuses, check runs, open PRs and pipelines are read 100 per page until a short page. Exactly 5,000 items pass. More than 5,000 is an error, not a silent cut, because a missed marker would post a second brief. The merge brief lists changed files up to a 20,000-character budget and then says how many more files it did not list, so a PR of 3,000 files still gets a brief.

## Wiring to the real cage

- `agent-works serve --mode cages --config <file.json>` runs HQ with this mode. The config names the host (`github` or `gitlab`), the repo, the base branch, the operator's clone (`source`), the author and reviewer worker names, the tickets, and optionally the model and the agent binary. HQ reaches the host through `gh api` or `glab api`, and logs every call to `<home>/api-calls.jsonl`.
- `server/agents/cage-shell.ts` gives the Claude Code runtime a real shell: it starts one cage per worker and task through the P1-1 sandbox driver and runs `docker exec -i` (or podman) in it. The prompt goes to the agent on stdin, so a large PR never reaches the argv limit.
- `POST /api/actions/allow {host, port?}` keys a website on `host:port`. The host is lowercased, its trailing dot dropped and an IDN name turned into its ASCII form, and the port defaults to 443. One validator (`server/sandbox/site.ts`) serves the API, the proxy denials and `driver.allow`, and ends with the proxy's own `parseAllowlist` as the final gate. It is a strict subset of what the proxy accepts in a hand-written allowlist file. It refuses a wildcard, a second line, `#`, whitespace and any character a host name cannot hold. A denial for a name it refuses, such as a wildcard CONNECT, still shows as a website item, with `allow: false`, and Allow refuses it. Allow appends the rule to the running Node proxy's allowlist file, which the proxy reads on every CONNECT. An IP literal or a malformed name is refused, because one bad line would make the proxy deny every request.
- `server/test/sandbox/cage-shell.test.ts` runs this on local docker with a scripted fake agent binary in the worker's home (not the real Claude Code): the agent reads its prompt from stdin and commits in the cage, a 3 MB review prompt reaches it, and a CONNECT that the proxy denied with 403 goes through to the upstream lookup (502 for a `.invalid` name) after Allow, while the same host on another port stays denied.
- A binary file is never read back as text. The reviewer's prompt names it as a binary file and shows no content. An author commit that adds a binary file fails the job, because HQ pushes text files only.
- The config refuses an author login equal to the reviewer login, and the cage shell keys each cage on worker and task, so the author and the reviewer never share a cage.

What is not wired yet:

- The real Claude Code binary has not run in a cage under HQ, because that needs the operator's login (gate P1-2). That `claude -p` reads the prompt from stdin when no prompt argument is given comes from the Claude Code docs; only the fake binary proves the wiring.
- The CLI config has one host account. Author and reviewer share the `gh` or `glab` login, so with the G1 default a box waits in `qc` (no approval from the author's own account).
- After an HQ restart, the cage for a fix round is a fresh export of the operator's clone, not the PR head. The push still builds on the PR head's tree, but the agent does not see its earlier round in the cage.
- A cage is released when HQ stops, not when its task ships.
- On GitLab, a reviewer's "changes" verdict is posted as a note and read back as a comment, so it starts no fix round. This gap predates this round. It is recorded here, not fixed.
- A GitHub tree too large to list in one call makes the push fail rather than guess.

## BLOCKED ATTEMPTS and the repeat pause (P2-2, round 2)

The first P2-2 round recorded every proxy denial as an F2 attempt and paused a worker on three identical ones. That contradicted the Allow flow above: a worker whose package manager retries a host that is not allowlisted yet is waiting on the operator, and three retries paused it, with nothing in HQ or the dashboard to resume it. The premise that every repeated denial is a worker stuck in a loop was false. Decided:

- **Every denial is listed on `/blocked`, but only a denial no Allow can fix counts toward the pause.** A denial with reason `not-allowlisted` for a name `siteOf` accepts is a website item. It waits on the operator, and the worker's retry goes through after Allow. It is listed, its repeat count shows, and it never pauses. Any other denial (a non-public address, an SNI mismatch, ECH, no SNI, plain HTTP, a name Allow refuses such as a wildcard) is not fixed by Allow, so three of them from one worker pause it.
- **Counts are windowed.** An identical attempt counts only against the same worker's attempts of the last 10 minutes (`REPEAT_WINDOW_MS`), so a repeat hours later or on another task does not add up to the old ones.
- **Allow clears.** `POST /api/actions/allow` drops the counts for that site and resumes the workers it paused (`BlockedLog.cleared`), then wakes the mode. `POST /api/workers/resume {worker}` stays for a pause the operator decides to lift.
- **Limit.** A hostile worker that retries a not-allowlisted name forever is never paused. The cost is a growing repeat count on one website item, and nothing leaves the cage, because the proxy denies every try. The operator sees the item and the count.

## Consequences

- A fix round is pushed by HQ through the host API from the files the author's runtime returns. The Claude Code runtime reads those files with git inside the cage, so the host never runs git over a repo an agent can write.
- The cross-runtime review in the spec cannot run while Codex is deferred. The reviewer runs on the same runtime under another worker name, and the merge brief and the snapshot say so.
- Webhooks are not wired into HQ yet. The mode polls every open PR (35 s by default), which meets the 60 s close budget measured in P0-4. Issue #8's unsigned event header in a file path therefore has no counterpart here: HQ writes no delivery file, and the parsers accept only the event names they know.
- A second Ctrl-C on `agent-works serve` exits at once (code 130) when the first one's clean stop hangs. This path has no test.
- Every live lane that needs a Claude agent still needs the operator's login (gate P1-2).
