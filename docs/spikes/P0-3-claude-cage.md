# P0-3. Claude Code runs in a cage with credentials blocked

This spike tests the protected-files layers in `AGENT_WORKS_PROMPT.md` section 4. It runs Claude Code 2.1.325 headless inside a docker cage on a claude.ai subscription login. It then tries to read fake credentials with the Read tool, `cat`, `cp`, `grep -r`, a redirect and a script that builds the file name.

The short answer is yes, with two hard rules, and with a limit on what is proven. First, no credential file may be reachable through git, because the mask covers files on disk and not git objects. Round 1 missed this: its harness committed the fixture with `git add -A`, and `git diff`, `git show HEAD:.env` and `git log -p` printed the canaries through every layer. Rounds 2 to 4 each added another list of places to check, and the verifier found the next place each time. The preflight (`git-scan.mjs`) is a best-effort, fail-closed check on the git dirs and loose stores it identifies by structure (a dir holding `HEAD`, `objects/` and `refs/`), read NUL-delimited. In each git dir it identifies it requires every ref to be a branch, tag or remote branch that peels to a commit, and every object to be reachable from those commits through a path in a commit tree, with no protected path. Tags on blobs, notes, replace, stash, original refs, dangling objects, a reflog longer than a fresh clone's, any form of an alternates file, shallow, grafts, linked worktrees, a symlinked `HEAD`, `objects` or `refs`, a bare repo or any unknown file or subdirectory inside a git dir (tested at six positions under `.git`, listed under the preflight bullets), and a loose object store or pack dir with no `HEAD` all fail, and so does anything the scan cannot parse, read or bound. It is not a proof that no secret is in the object store. The scan runs git inside a bounded throwaway container, never on the host's agent-writable state and never in the hook. Second, only layer 2, the empty read-only bind over each protected file, stops a script that builds the file name. Layer 4 is a best-effort text matcher. So `subagents-local`, which has no mask, cannot promise protection from a script, and P0-6 must rate it best effort, as N-1 in `docs/sources.md` predicts.

What was observed, and only this: in the live lanes and in CI, on a repo the preflight accepted at the time, with all layers on, the plain paths, the nine git readers listed in `L2-git-readers`, a git commit by the agent and the glob reads printed no canary. The preflight is a point-in-time scan, so the guard now takes its verdict per request and the harness recomputes it before every model call and after the agent commits (`L2-commit-a` shows the repo going not clean on the second reflog entry, and the guard then denies every git command). Not shown is that no sequence of agent actions between two scans can make a git reader print a protected file, and nothing about a path the matcher does not parse. When the verdict is false or unknown, the guard denies every command that names git, which is a text rule: a git started through an interpreter that builds the name `git` at run time is outside it, and only the preflight (refusing to start on an unclean repo) and layer 2 bound that.

**Premise check and recommendation.** The premise of rounds 1 to 3 was that a repo's git store can be judged by listing where a secret might be. Three rounds of that left another place each time, and round 4's accounting rule did too (a symlinked `HEAD`, a bare repo inside `.git`, an alternates symlink, a loose store with no `HEAD`; rounds 5 and 6 flag those and the layouts listed under the preflight bullets, and nothing else is claimed). The scan is a best-effort check on the git dirs and loose stores it identifies by structure. It cannot see a secret in a commit or tag message, a credential under a harmless path name (a `config.txt` holding a key, invisible to every layer here), a git store the structural discovery does not recognize, or a layout nobody tested. The product should not scan a developer's repo to decide it is safe. It should create the cage's repo as a fresh export (`git archive` of the commit to run on, or a `git init` plus one commit of the working tree minus the protected files), so the object store has one commit, no reflog, no stash, no notes, no alternates and nothing to account for. The scan stays as a check on that export and on the repo after the agent has written to it.

`cage-lanes.mjs` needs no login and no model. It commits the fixture with every protected file ignored and untracked, runs the contained preflight on it (and on a repo with a planted `core.fsmonitor`, a repo whose `.env` lives only in the reflog, six repos that hold a protected blob only through a blob tag, an annotated blob tag, notes, replace, a directory name with a newline in history, and a bare `.gitdata`, and a missing path; `L1-preflight-complete`), then builds `spikes/P0-3/Containerfile` (Node 24 on Debian bookworm slim, tmux, git, Claude Code 2.1.325, user `node`). It starts a masked cage and an unmasked control cage, drives the hook server with scripted tool calls from inside the cage, and prints one `PASS`, `FAIL` or `NOT-RUN` line per attack path. CI runs it on docker and podman in `.github/workflows/p0-3-cage.yml`.

`run-agent.mjs` runs the model lanes. It needs a docker volume that holds a claude.ai login, and it spends subscription usage, not money. It never starts, writes to or cleans inside the operator's cage or that volume. Each lane starts its own throwaway cages, labeled `agent-works.p0-3=lane`, `agent-works.run=<id>` and `agent-works.project=p0-3-live`, and removes only those. The login volume is mounted read-only by subpath at `/creds`, and the throwaway home links `.credentials.json` and copies `.claude.json` from it (S-70, S-72). Managed settings go into the throwaway cage's own `/etc/claude-code/`. The guard server binds the docker bridge gateway and requires a per-run token in an `X-Guard-Token` header (S-77), because every default-bridge container can reach that address. The URL carries no token, so the hook error text Claude Code prints names none. It runs `claude -p ... --output-format stream-json --verbose --model haiku`, one call per attack. CI cannot log in, so it never runs these.

| 3. Deny rules | 64 `Read` and `Edit` rules in managed settings, from the built-in pattern list | `settings.mjs` |
| 4. PreToolUse hook | An `http` hook with `onFailure: "block"` posting to `hooks/guard-server.mjs`, which answers `deny` with the layer name. While the verdict is true it keeps the reader rules (`-C` or `--work-tree` anywhere other than the workspace root, `--git-dir` anywhere other than the root's own `.git`, any git run after a `cd`, `pushd` or `popd` to anywhere other than the root, a `git config`, `-c` or `--config-env` that sets `core.worktree`, `core.gitdir`, `core.bare`, `include.path`, `includeIf.*` or `extensions.*`, `git worktree`, `update-ref` or `symbolic-ref` with a ref operand outside `refs/heads/`, any `GIT_CONFIG_*` variable, `git grep --no-index`, `git ls-files -o`) and denies any command or tool call that names a protected path. | 5. Pre-commit guard | Not built. Layer 5 of the spec is out of scope for this spike. The harness keeps protected files untracked, so `git commit -a` cannot commit an emptied `.env`. | none |

The git preflight is a precondition for layer 2 and for layer 4's git rule. Round 2's check missed a reflog-only credential, a dangling blob and a submodule (S-75), and round 3's list missed a directory name with a newline in history and reflog, a git dir not named `.git`, and a blob that only a tag, a note or a replace ref holds (S-78). Round 4 replaced the list with an accounting rule and round 5 tightened the discovery; both are in `git-scan.mjs`, and neither is a proof:

- git dirs are found by structure (`HEAD` file, `objects/` and `refs/` dirs), never by name, by a walk that does not follow symlinks; `.git` files must point at a discovered git dir inside the repo, a dir named `.git` that is not a git dir fails, and each git dir is walked by name only (`readdir`, no file contents, counted against the 250000 entry cap, over it is not clean). Inside an identified git dir only known entries are tolerated: the top level holds git's known files and dirs, `objects/<2-hex>/` only files named by 38 hex chars (or git's `tmp_obj_` names), `objects/pack/` only `pack-<hex>.(pack|idx|rev|bitmap|mtimes|keep|promisor)`, git's `tmp_pack_`, `tmp_idx_` and `tmp_rev_` names and `multi-pack-index` files (also `multi-pack-index-<hash>.bitmap`), `objects/info/` only `packs`, `commit-graph`, `commit-graphs/` and the alternates files, `info/` only `exclude`, `refs`, `attributes`, `sparse-checkout` and `grafts`, `hooks/` and `branches/` only files, `logs/` only `HEAD` and `refs/`, `refs/` only the dirs git defines. Any other file or any subdirectory there, such as a bare repo at `.git/objects/pack/v.git`, `.git/objects/ab/v.git`, `.git/objects/info/v.git`, `.git/refs/v.git`, `.git/hooks/v.git` or `.git/logs/v.git`, fails, and a git dir nested in another one fails unless it is a submodule git dir under `modules/`. Tested: a fresh repo, a fresh clone, a repo after `git gc`, after `repack -a --write-bitmap-index`, `repack --write-midx --write-bitmap-index`, `multi-pack-index write --bitmap` and `commit-graph write`, and a rerere merge stay clean, and a `--recurse-submodules` clone with a submodule under `modules/` is clean only after the submodule reflog is expired; the six bare repo positions above and stray files in `objects`, `objects/pack`, `objects/<2-hex>`, `info`, `logs` and the git dir top level fail. Layouts not in that list (a repo from another git version, `rebase-merge/` contents, `rr-cache/`, `lfs/`, `fsmonitor--daemon/`, `sequencer/`) are tolerated by name and not walked for structure, only for a nested git dir. `HEAD`, `objects` or `refs` that is a symlink, in a dir that has at least two of the three, fails and is never followed. Anywhere in the tree outside the identified git dirs, a `pack/` dir holding `.pack` files, or a dir whose children are 2-hex dirs holding 38-hex files, fails; both are heuristics;
- every ref in each git dir must be under `refs/heads/`, `refs/tags/` or `refs/remotes/` and must be a commit or an annotated tag that peels to a commit; `refs/notes`, `refs/replace`, `refs/stash`, `refs/original`, and a tag on a blob or tree fail;
- the accounted set is `rev-list --objects --no-object-names --branches --tags --remotes` (newline-safe), and every object from `cat-file --batch-all-objects` must be in it, so a dangling, reflog-only, staged-only or path-less object fails;
- paths come from `diff-tree --stdin -r -z --root -m` over every commit (plus `--all --reflog` so a reflog-only commit is named) and from `ls-files -z --stage`, both NUL-delimited, and are matched with the same `isProtectedPath` the hook uses;
- a reflog with more than one entry in any file fails (a fresh clone has one per ref), and so do `objects/info/alternates`, `http-alternates`, `shallow`, `info/grafts` and a `worktrees/` dir, found with `lstat`, so a file, an empty file, a symlink or a dangling symlink all fail and the alternates path is never resolved;
- a missing or non-directory path, a directory with no git dir of its own, a git failure, a timeout (the container itself is killed at `timeoutMs`, SIGKILL on the engine client and `rm -f` by name; a FIFO planted as `packed-refs` now returns not clean at 3 s instead of running 120 s), an output over 512 MiB, an unreadable directory, or more than 250000 entries is "not clean". `git` runs with `GIT_NO_REPLACE_OBJECTS=1` and the hardened flags below.

What the scan does not do: it matches protected names, so a credential under a harmless name is not found, it does not read commit or tag messages, it does not recognize a git store whose layout it was not tested on, and its two loose-store checks are heuristics. An agent that commits makes the reflog longer than one entry, so after any agent commit the repo is not clean until the host runs `git reflog expire --expire=now --all`; the harness recomputes the verdict before every model call and the guard then denies all git commands, which is the intended fail-closed cost.

The product preflight (plan lane 9) must run this full scan, not `trackedProtected`, and must not start the cage when it is not clean. The recommendation above (a fresh export: one commit of the tree minus the protected files, no reflog, no stash, no alternates) leaves nothing for the scan to account for, and the scan is then a check on that export and on the repo after the agent writes.

Decision on layer 2 for `.git`: not masked. Git must keep working in the cage, and the mask hides files, not objects. The preflight is what closes it, and the harness refuses to start a cage on a repo that is not clean, so a reader cannot print a protected file from the repo as scanned. That is the claim, and it is a statement about the scanned state and the git dirs the scan identified: between two scans the agent can write the repo, which is why the verdict is recomputed before every model call and per lane, and why the hook's git rule is the second gate. The guard server holds `gitClean`, `setGitClean` changes it, and while it is false or unset the guard denies every command that names git.

Where it runs matters more than what it checks. Round 2 ran `git -c safe.directory=* -C <repo> ls-files` in the guard on the host, against a repo the agent can write. The agent set `core.fsmonitor=<cmd>` in the bind-mounted `.git/config` and the guard ran it as the host user (S-74). The guard is run under `node --permission` without `--allow-child-process`, and the round 5 test makes any attempt to spawn observable. `spawn-audit.mjs` is preloaded with `--import` and wraps `exec`, `execFile`, `execFileSync`, `execSync`, `fork`, `spawn` and `spawnSync` on the shared module, so a call is written to an audit file before the permission model denies it, and a swallowed `ERR_ACCESS_DENIED` still leaves a record. The test drives `checkToolCall` (`spawn-driver.mjs`) and `guard-server.mjs` with `--git-clean` on and off and fails on any record. The round 4 verifier's `import(['node:child','process'].join('_')).then(...)` one-liner in `checkBash` passed the old test and fails the new one (S-80). A static check also bans dynamic `import(`, `process.binding`, `getBuiltinModule`, `createRequire`, `Function(`, `eval(`, `require(` and `child_process` in the two guard modules. This makes spawning observable on the paths the tests drive; it does not prove that no spawn path exists. The permission model, not the test, is what refuses a spawn. `git-scan.mjs` runs in a throwaway container named for the run, with the repo mounted by `--mount type=bind,...,readonly` (a missing path errors and creates no root-owned host dir, S-79), no network, no capabilities, a read-only root, `--pids-limit 256` and `--memory 2g`, and the harness removes the container by name after every scan, including after a timeout, with `-c core.fsmonitor=false -c core.hooksPath=/dev/null -c protocol.allow=never`, `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL=/dev/null`. `L1-preflight-contained` plants `core.fsmonitor` in a repo and shows a plain `git diff` in the container runs it while the hardened scan does not. The unit test for the exact round 2 repro fails against any change that runs git in the hook. The harness itself runs host git in two places, on repos it made and no agent has touched: `commitFixture` runs `scanRepo` on the host right after it creates the fixture (the host scan is hardened, but it is not the contained scan; `run-agent.mjs` and `cage-lanes.mjs` rescan in the container before any agent runs), and `cage-lanes.mjs` builds its variant repos with host git. Round 3 left a host `git diff --stat` in the `baseline` lane after the agent had written the repo; round 4 reads the file instead.

If a protected file is found, the remediation is on the host, before the cage starts: `git rm --cached <path>` (the in-cage hook blocks that command, because it names the path). If the file was ever committed, rewrite history, then run `git reflog expire --expire=now --all` and `git gc --prune=now`, because the reflog and loose objects keep the old blob until they are expired and pruned. `git rm --cached` alone is not enough.

Deny rules cannot express `.env.*` without also hiding `.env.example`, because an allow rule cannot carve an exception out of a deny rule (S-08). Layer 3 lists the common names (`.env.local`, `.env.production` and so on). The hook matches the rest.

## Known limits and best effort for P0-6

Layer 4 is a text matcher over shell commands and is best effort by design. Six rounds of widening it each found another shell form that sidesteps one rule, and the file mask (layer 2) held every time. The limits below are grouped as preflight scope, git gate, matcher, config and ref writes, and scan cost. P0-6 must rate `subagents-local` (no mask) as best effort for every class below; only the layer 2 mask closes them in a cage, and layer 4 does not guard the cage home at all (layer 1, the unmounted host home, and the fresh cage home do).

What the matcher does handle (each is a test in `leaks.test.ts`, `round3.test.ts`, `round5.test.ts` or `round7.test.ts`): quotes, backslashes, `$'..'` with `\xNN`, octal and `\u` escapes, braces, globs in the last path segment, `NAME=value` assignments, one shared normalization that drops leading assignments, `{`, `!`, `if`, `then`, `do` and the wrappers `env`, `sudo`, `doas`, `nice`, `nohup`, `timeout`, `command`, `builtin`, `exec`, `time`, `stdbuf` and `setsid` with their option values (so `A=1 git -C /srv log`, `env -u X git ...` and `sudo -u root git ...` meet the same git rules as a bare `git`, with the verdict true or false), `$(...)` and newline-separated commands, the string after `sh -c`, `bash -c`, `zsh -c`, `dash -c`, `su -c` and `eval` (to depth 4), interpreter text (`python -c`, `node -e`, `awk`) that names a protected file, `tar`, `zip`, `cp -r` and `rsync` over a directory that holds one, `grep -d recurse`, case-insensitive names and `.envrc`, `git` readers as described above, and for `Grep` and `Glob` any glob, brace list or negation that could match a protected name.

### Preflight scope

- The scan matches protected names. A credential under a harmless name (`notes.txt`, `config.json`, a key in a source file) is not found, commit and tag messages are not read, and objects under a harmless name are outside it: a bundle or raw pack stored as `docs/archive.dat` or `assets/x.bin`, read with `git fetch docs/archive.dat` or `git unpack-objects < assets/x.bin`, can bring protected blobs into the store the agent then reads. The hook does not parse the file operand, and `protocol.allow=never` applies to the scan only.
- Symlinked git dir entries, unknown entries inside an identified git dir and nested git dirs are flagged, not followed. Loose object stores and pack dirs outside an identified git dir are flagged by a heuristic that a store with other file names, or one split across directories, can avoid. A split store (a `commondir` file, a `gitdir` file or an alternates file pointing elsewhere, or objects in a sibling dir) is caught only where the scan sees the file: `commondir` and `gitdir` are tolerated, and the scan never resolves what they point at.
- The scan is a check at cage start, recomputed by the harness before each model call. A layer 4 bypass plus `git add -f` of an unmasked file puts a protected file into git; any form of an alternates file is refused (never resolved); objects borrowed in a way git does not record in the store are not seen.
- A fresh `git clone --recurse-submodules` is not clean until the submodule's reflog is expired (`git -C <submodule> reflog expire --expire=now --all`), and the superproject's reflog too if it has more than one entry.
- The mask is a file list taken at cage start. A protected file created later is not masked until a re-scan, and a directory that is unreadable at cage start makes `maskMounts` throw rather than skip. The scan cap is 250000 entries; over it the hook blocks the recursive search and the harness refuses to start the cage. `node_modules` and `.git` are not scanned by the recursive-search rule, on purpose (a package that ships a test key would make every search look protected), so a credential planted under `node_modules` is covered only by a command that names it, and the mask does not cover it either.
- The layer 3 deny rules list names and are case-sensitive: `.env.vault` has no rule, and `.ENV` on a case-insensitive host is not covered. The hook covers both.

### Git gate

- With the verdict false or unknown the gate is text-based: a git started through an interpreter that builds the word at run time (`python -c "os.system('g'+'it log -p')"`), a build tool that runs git, `printf 'g\151t log -p' | sh`, `base64 -d | sh` and `'GIT_'+'DIR'` are outside it, and so is a `.git` object read through an interpreter (zlib). Only the preflight and, for working-tree files, layer 2 bound those.
- With the verdict true the gate denies `GIT_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR` and `GIT_CONFIG_*` anywhere in a command, and `--git-dir`, `--work-tree` and `-C` that point anywhere other than the root's own `.git` (for `--git-dir`) or the root, and any git run after a `cd`, `pushd` or `popd` to anywhere but the root, an `env -C` or `sudo -D` to anywhere but the root, or a `cd` in a nested `sh -c` or `eval`. A `cd` anywhere in the command (after `{`, `if`, `then`, `do`, `!`, `&&`, `||`, `;`) taints git later in the command. Workflow cost: the agent cannot run git inside a subdirectory or a submodule checkout; it runs git from the root, with paths (`git log -p -- sub/file`).
- Both states of the verdict go through the same `normalize` step before any git rule runs, so an assignment, a wrapper or a wrapper option value in front of `git` no longer hides it. `env -S 'string'` is not unpacked.

### Matcher

- Shell-grammar forms the text matcher cannot enumerate: compound commands it does not split, `eval` of a built string, process substitution, here-docs and here-strings (`sh <<<`), aliases, shell functions, `IFS` tricks, `script -qc` and `busybox sh -c`. Each can hide a protected name or a git word. Only layer 2 closes them.
- A script that builds the name (`'.'+'env'`, `chr(46)`), `$(printf ...)`, a base64 pipe, a downloaded binary, a heredoc fed to an interpreter that reads a file name from another file, a variable set outside the same command, and an unset `${x}` inside a name.
- A symlink in the repo (`innocent.txt -> .env`, or a symlinked directory that `grep -R` follows): the guard does not follow symlinks out of the workspace.
- `xargs`, `ls -a | xargs grep KEY`, a glob in a directory segment (`*/x`), and a command word built by an expansion (the git gate denies the last only while the verdict is false or unknown).
- An MCP tool that takes a directory, a URL or an id: only a string argument that is a protected path is checked.
- Layer 4 does not guard the cage home. The host home is never mounted (layer 1) and the cage home is a fresh volume; a verifier read a canary there through a `git add -f -A :/` with a redirected work tree, which the config rules below now partly gate and the unnamed forms do not.
- False positives are the cost of the recursive-search rule and are kept. A `.env` at the repo root makes `find . -name '*.js'`, `rg TODO`, `grep -r` and a plain `Grep` call denied, because the walk finds a protected file under the root. With layer 2 working (`cages` mode) the rule can be relaxed, because a masked file prints nothing. Only `subagents-local`, which has no mask, needs it, and there it is best effort.

### Config and ref writes

- Keys that redirect git are gated only for `core.worktree`, `core.gitdir`, `core.bare`, `include.path`, `includeIf.*` and `extensions.*` (through `git config`, `-c` and `--config-env`), and `GIT_CONFIG_*` is denied. Any other write to `.git/config` is outside the gate: a shell redirect, `sed -i`, `tee`, `cp`, a script, or the Write or Edit tool (the deny rules cover names, not `.git/config`) can set `core.worktree`, then `git add -f -A :/` stages files from outside the repo. The verifier printed a cage-home canary this way.
- `git config --edit` and `GIT_EDITOR` (or `core.editor`) run an editor the agent chose, so they can write `.git/config` too. The rest of the class is not gated: `core.attributesFile`, `core.excludesFile`, `core.fsmonitor`, `core.sshCommand`, `filter.*`, `diff.external`, `alias.*` and `url.*.insteadOf`.
- `git update-ref` and `git symbolic-ref` are bounded to `refs/heads/`, `HEAD` and object ids; other ref-writing commands (`git tag`, `git branch`, `git stash`, `git notes`, `git replace`, `git fetch <ref>`) are not gated.
- The hook cannot see a write it does not match. The check is the preflight verdict the harness recomputes before each model call, and the guard then denies all git while the repo is not clean.

### Scan cost

- An agent commit makes the reflog longer than one entry, so after any agent commit the repo is not clean until the host runs `git reflog expire --expire=now --all` (and `git gc --prune=now` for a dangling object, as after a rerere merge); the guard denies all git commands meanwhile. This is the intended fail-closed cost.
- Normal git output the scan accepts by name: `objects/pack/multi-pack-index-<hash>.bitmap`, top-level `MERGE_RR`, `rr-cache/`, `lfs/` and `fsmonitor--daemon/` (tested clean after `git multi-pack-index write --bitmap`, `repack --write-midx --write-bitmap-index`, a rerere merge, and with an `lfs/objects` tree and a cookie dir). They are tolerated by name and walked only for a nested git dir (one in `lfs/` or `fsmonitor--daemon/` fails), so a file inside them is not inspected: `rr-cache/` holds conflict text and `lfs/objects/` holds file contents by hash, which can carry a protected file's content under no path. A running fsmonitor daemon leaves a socket entry in the git dir top level, which fails until it stops. That is the cost of allowing them.
- `toolProbe` fails when the tool output holds a `PreToolUse:<tool> hook error` line.

### Guard server and test limits

- The guard binds the docker bridge gateway, which every default-bridge container can reach. The `X-Guard-Token` header separates other containers from the log and from the verdicts. It does not separate the agent from its own hook: the managed settings file is mode 644 in the cage so Claude Code (user `node`) can read it, and so can the agent, which can then forge events or spend the log budget. A hostile agent that reads the token controls only the guard's log, not the verdicts.
- The log has two budgets: 16 MiB for events and 4 MiB for denies. Forged events cannot hide a real deny, but a forger that can reach the guard can spend the deny budget. `stats()` counts every deny, logged or not, and that is the record to trust.
- A hook that does not answer in time blocks every tool call (S-73), so a guard outage stops the agent and does not open the gate.
- The hook sees only the workspace the server maps (`workspace` and `root`). A real HQ needs the same mapping, or a hook that runs inside the cage.
- The test cage ran on the default bridge with no firewall (P0-2 covers egress), the model lanes used `--model haiku` (a stronger model may try more paths), and the unit tests that read a real directory or start the hook server skip on Windows.

The last line: the product's cage repo must be a fresh sanitized export, and layer 4 must be treated as best effort that raises the cost of a leak and is not a boundary.

## Decision for the operator

P0-3 shows that layers 1 to 3 and the mask are the boundary, and layer 4 is best effort. The product spec's `subagents-local` mode has no mask, so there only layers 3 and 4 apply, and the threat model (P0-6) must rate it best effort that the operator accepts or declines.
